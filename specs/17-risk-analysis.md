# 风险分析

> 来源：全部 Specs。风险覆盖需求、建模、架构、数据库、权限、Agent 使用六类。

## 风险登记表

| 编号 | 类别 | 风险描述 | 影响 | 概率 | 应对措施 |
|---|---|---|---|---|---|
| R-001 | 需求 | 读者类型 / 借阅规则数值理解偏差，导致规则实现错误 | 高 | 中 | 规则写入 `borrow_policies`，人工审查确认 |
| R-002 | 需求 | 罚款规则按"借出物类型"而非"读者类型"，易混淆 | 高 | 中 | 明确区分：读者类型→借阅规则，借出物类型→罚款规则 |
| R-003 | 需求 | "借书必须由管理员代理"被误解为读者可自助借书 | 高 | 低 | 在用例与 API 中强制携带 `librarian_id` |
| R-004 | 建模 | 领域类照搬数据库表，丢失业务概念（如 BorrowPolicy） | 中 | 中 | 领域模型评审，检查是否有"规则类" |
| R-005 | 建模 | 过早把 Controller / Repository 混入领域类图 | 中 | 中 | 类图只含业务概念，设计类另置于详细设计 |
| R-006 | 架构 | 业务规则写进 Controller，破坏分层 | 高 | 中 | 代码评审检查 Controller 是否只做转发 |
| R-007 | 架构 | 借阅 / 罚款规则散落多处，难以维护 | 中 | 中 | 集中到 `BorrowPolicy` / `FineRule` 策略 |
| R-008 | 架构 | 事务边界不清，借书失败后副本状态未回滚 | 高 | 中 | 事务设在应用服务层，失败统一回滚 |
| R-009 | 数据库 | 借阅证号 / 条码未设唯一约束 | 中 | 低 | 建表时加 UNIQUE 约束 |
| R-010 | 数据库 | `loans` 无法区分借出 / 已还 / 超期 | 中 | 低 | 使用 `status` 枚举 + `is_overdue` |
| R-011 | 数据库 | 预约无法表达多人排队 | 中 | 中 | 使用 `created_at` + `queue_position` |
| R-012 | 权限 | 普通读者调用管理员接口 | 高 | 中 | 服务端校验角色，越权返回 403 |
| R-013 | Agent | Agent 编造需求 / 擅自修改 baseline specs | 中 | 中 | 人工审查 diff；baseline 打 tag；宪法约束 |
| R-014 | Agent | Agent 生成的字段名与后端不一致，导致调用失败 | 中 | 高 | 字段名以 API 规范为准，前后端对齐 |
| R-015 | Agent | 测试未覆盖异常流程，缺陷遗漏 | 中 | 中 | 按测试计划覆盖失败场景 |

## 高风险项优先级

1. **R-003 权限与代理借书**——影响范围最大，优先在用例与测试中固化。
2. **R-008 事务一致性**——直接影响数据正确性。
3. **R-014 字段名一致**——AI 辅助开发中最常见的集成问题。
